# SashaTel — продуктовая спецификация v1.0 (история) + утверждённый контракт v1.1

**Статус:** согласованная целевая UX/продуктовая архитектура; **не** утверждение о готовности реализации.  
**Дата:** 17.11.2026. **Область:** Web SaaS, Desktop, телефония, интеграции, биллинг.  
**Принцип:** каждый раздел решает самостоятельную задачу. Не добавлять функции «на будущее» в интерфейс без сценария.

## Продуктовый контракт v1.1 — 19.11.2026 (утверждено)

Этот раздел имеет приоритет над несовместимыми историческими формулировками ниже. Утверждение продуктового поведения **не означает**, что Backend, PBX, биллинг или тесты уже реализованы.

**Терминология номеров.** Во всех пользовательских интерфейсах, API-документации и новых комментариях используем только **«Активные»** и **«Пассивные»** (`active` / `passive`). «На удаление» — прежнее название, оставленное ниже исключительно как факт истории обсуждения; **не использовать как актуальный статус**. Пассивный номер исключается из **новых** инициаций немедленно, но остаётся у оператора до отдельного подтверждённого действия удаления. Перевод в пассивный не обрывает активный разговор. Удаление у оператора, наличие спам-метки и активность карусели — независимые факты. Уже зарезервированный, но ещё не отправленный вызов должен повторно проверить статус номера и отклониться при `passive`. Все подтверждённые 150 номеров, включая расчётный запас +50%, вправе быть одновременно активными и распределять нагрузку равномерно.

**Транки и сотрудники.** Несколько SIP-транков на организацию; первый рабочий транк становится транком организации по умолчанию. Новый сотрудник наследует его автоматически, персональный override необязателен; администратор может массово назначить другой. `effective_trunk_id = employee.trunk_override_id ?? organization.default_trunk_id`; сервер проверяет действительность назначения и разрешённый оператором Caller ID. Desktop не выбирает транк на каждый звонок. **Без автоматического переключения на другой транк при ошибке.** Фактический `trunk_id` обязательно хранится в событии, карточке, истории, статистике и CSV; есть фильтр по транку. Изменения назначения аудитируются. UIS на Timeweb — тестовый пример такого же клиентского SIP-транка, но успешная регистрация не равна готовности к звонку.

**Лимит карусели.** Максимум **8 инициаций на один физический Caller ID за календарный день Europe/Moscow**, включая одновременные запросы. Атомарный `hold → commit → release`; повтор идемпотентного запроса не создаёт нового вызова. Списание перед первым долговечным исходящим dispatch, не при простом запросе. Учитывать один и тот же физический номер при возможном использовании несколькими организациями/транками. Параметры оператора и его разрешения обязательны.

**Единые результаты вызовов.** Пользовательские статусы: **«Дозвон»** (подтверждён человек), **«Автоответчик»** (подтверждена машина), **«Недозвон»** (ответа не было), **«Отклонено»** (зафиксирован отказ, не обязательно сознательный сброс адресатом), **«Ошибка»** (технический сбой), **«Не распознано»** (техническое соединение было, но тип отвечающей стороны не подтверждён). Не объединять «Не распознано» с автоответчиком, не присваивать «Дозвон» на основании только SIP 200. Отмена до ответа по действию сотрудника — отдельная причина `cancelled_by_agent`, не ошибка качества номера; завершение начатого разговора — отдельный `hangup_actor`, если направление достоверно известно. Сохранять SIP/Q.850, события ARI/CEL/CDR и доказательства классификации. Статусы взаимно исключаются, а внутренние причины/каналы не становятся дополнительными произвольными статусами UI.

**Биллинг.** SashaTel — постоплата **3 ₽ за тарифицируемую минуту только подтверждённого разговора с человеком**. «Автоответчик», «Недозвон», «Отклонено», «Ошибка», «Не распознано» не создают тарифицируемых человеческих минут. Добровольные частичные авансы уменьшают задолженность/будущие начисления **только после подтверждённого поступления денег**. Нет обязательного пополнения, предоплатного ограничения на создание звонка или кредитного лимита. Счёт и УПД за оказанные услуги — по окончании периода, оплата в течение 5 рабочих дней, просрочка блокирует новые вызовы, не обрывая активные. Тариф стороннего оператора и его CDR отдельно. Точность и округление тарифицируемых минут, спорные классификации и налоговые правила требуют проверки до коммерческих начислений, **но не разрешают подменить утверждённую модель предоплатой**.

**Диагностика транков.** Единые технические статусы с доказательствами и кодами; отдельная документация с возможными причинами и последовательностью исправления. Без AI-рекомендаций. SIP-регистрация и готовность реального PSTN-вызова — разные состояния.

**PBX.** Архитектура рассчитана на несколько PBX-инстансов (`pbx_instance_id`, глобальные ограничения и события), первоначально развёртывается один действующий Asterisk. ARI доступен только защищённому серверному worker, без пользовательских dialplan-обходов. Изменения PJSIP должны выполняться через версионированный provisioning, а не через постоянное ручное редактирование VPS.

**Наследование и приёмка.** PR #14, #15, #28, #29 и UI обязаны ссылаться на этот контракт. Старый `wallet.available >= reserve_per_call` и инкремент `number_attempts` при authorize — **известные несовместимые реализации**, не разрешённые для коммерческого деплоя. Код нужно исправить, прогнать PostgreSQL concurrency/RLS, ARI recovery, SIP/CLI и биллинговые тесты; никаких утверждений о готовом end-to-end до реального прохождения.

## 1. Продукт и границы

SashaTel — B2B-платформа для исходящих звонков сотрудников через Desktop с Web SaaS для администрирования организации, транков, Caller ID, аналитики, истории, интеграций и оплаты. Внешний оператор связи (предполагается Билайн) отдельно оказывает и выставляет клиенту услуги связи. Desktop — рабочее место для звонков, а не интерфейс конфигурации SIP.

**Навигация Web SaaS:** Статистика; История звонков; Транки; Сотрудники; Интеграции; Биллинг. Настройки аккаунта и организации — в меню профиля, не отдельный раздел боковой панели. Вверху сайдбара — выбранная организация, визуально отделённая от разделов. Ссылка «Скачать приложение» — в меню профиля. Общий выбор периода — нормальный календарный диапазон даты/времени, **без** пресетов 7/30/90 и лишних строк поиска.

## 2. Регистрация, организации и доступ

- Регистрация **только в Web**: email + пароль; проверка email кодом. В верификационном письме вторичной ссылкой — загрузка Desktop, главная цель письма — подтверждение email.
- После регистрации: «Добро пожаловать, Имя!» → создать организацию либо ожидать приглашения.
- Создание организации: ввод ИНН → подтянуть реквизиты через DaData → подтверждение. Создатель автоматически становится **Владельцем**, организация сразу появляется во внутренней админке SashaTel. ИНН сам по себе не доказывает полномочия; требующие проверки действия проектируются отдельно.
- Один глобальный аккаунт/email может состоять в нескольких организациях; при необходимости пользователь выбирает организацию.
- Роли: **Владелец**, **Администратор**, **Сотрудник**. Один Владелец на организацию. Администраторы управляют сотрудниками и друг другом, **но не** Владельцем/правами Владельца. Передача владения атомарна, с подтверждением; бывший Владелец становится Администратором.
- Приглашение только по email. Сотрудник принимает приглашение через Web; письмо содержит ссылку загрузки Desktop. Таблица сотрудников: **Сотрудник | Email | Роль | Статус присутствия**. Ранее минимальная таблица была без статуса; новый статус явно добавлен последующим решением. Не добавлять переключатель «доступ к звонкам».
- Пароль/email меняет сам пользователь; изменение email с подтверждением; восстановление пароля по email; администратор вправе завершать пользовательские сессии, но не знать/устанавливать пароль. Удаление сотрудника отменяет будущий доступ, история звонков сохраняется.
- Статусы присутствия **автоматические**: 🟢 «В сети» (Desktop подключён, вызова нет), 🟡 «На линии» (исходящий вызов с момента набора, включая ожидание ответа и разговор), ⚪ «Не в сети» (Desktop отключён). Не ручные.

## 3. Desktop

Три вкладки: **Набор | История звонков | Настройки**. Сразу после авторизации открывается «Набор». Вход существующим аккаунтом; «Зарегистрироваться» и восстановление пароля ведут в Web. При нескольких организациях выбирается организация. SIP-учётные данные в Desktop не вводятся; исходящий Caller ID выбирает система автоматически. Сотрудник видит в Desktop **только свои** звонки. Вызов инициируется **только из Desktop**; click-to-call/виджеты amoCRM и Битрикс24 отложены.

**Критерий безопасного запуска:** реальный вызов допускается только при проверенных доступе, состоянии организации, транка и телефонной инфраструктуры; неподключённый Backend/ARI не должен имитировать возможность звонка. UI Desktop готовит отдельный исполнитель, подробный дизайн не входит в этот документ.

## 4. Транки и Caller ID

Сайдбар **«Транки»** → список транков и «Создать транк» → при выборе транка: **«Управление» | «Номера» | «Информация»**.

**Управление**
- Включить/отключить возможность *новых* исходящих звонков через транк; текущие разговоры не рвать.
- **Одно** автоматическое правило перевода номеров в статус «Пассивные»: когда число инициаций по номеру достигло заданного N **и** дозвон ниже X%. Оба порога задаются клиентом; проверка только после достаточной выборки. Правило не создаёт у оператора мгновенного удаления; заявка попадает во внутреннюю очередь операторских действий.
- Обновление SIP-параметров/секрета; удаление транка с подтверждением и проверкой последствий.

**Номера**
- Системная **автоматическая карусель Caller ID**, без ручного выбора у менеджера, без персонального закрепления номера на MVP. Доступные номера должны быть разрешены провайдером для конкретного транка.
- Фильтры **«Активные» / «Пассивные»**. Пассивный номер немедленно исключён из новых инициаций, но необязательно удалён оператором. Фактическое удаление — отдельный процесс.
- Колонки **Номер → Спам-метка → Инициации → Ответы → Дозвон**, с дозвоном крайним справа. Дозвон = ответы / инициации; при нуле инициаций «—». Для неизвестной спам-метки показывать «—», а не «чистый». Источники Яндекс / Т-Банк рассматривались, но доступность, правомерность и частота проверки (~1 раз/мин обсуждалась) требуют проверки.
- Выбор периода влияет на статистические показатели, а не на текущую спам-метку. Экспорт CSV с учётом периода/фильтров, включая статус номера.

**Информация**
- SIP host/port/transport, режим авторизации, диагностический статус регистрации и доступности исходящего вызова, коды ошибок, технические данные. Различать «включён», «зарегистрирован» и «готов к вызову». Пароли не раскрывать; диагностику не дублировать во вкладке «Управление».

## 5. Статистика

Сохраняем существующую визуальную концепцию: **KPI → график → круговая диаграмма итогов набора → таблица сотрудников**; без отдельной вкладки AI-аналитики.

- Основные показатели: **+ минуты**, **+ инициации**, **+ ответы** (плюс перед абсолютными значениями как визуальная подача, **не** прирост к предыдущему периоду), **дозвон %**. Средняя продолжительность разговора — вспомогательная метрика.
- График динамики с переключением измерения (дозвон/инициации/ответы/минуты).
- «Итог набора» — технически и/или достоверно классифицированные исходы (человек, автоответчик, не ответили, занято/сброс, недоступен, номер не существует, отклонено оператором, ошибка транка). **Не** использовать бизнес-исходы «Назначена демонстрация», «Заинтересован», «Отказ». «Ответил человек» допустимо только при надёжной классификации, а не просто по SIP 200.
- Таблица сотрудников с набором, дозвоном и средней длительностью, сортировка.
- Фильтры дата/**время**, сотрудник, транк, результат при необходимости. Экспорт CSV.
- Согласовать единую семантику «инициация», «ответ», «длительность разговора», «тарифицируемая минута» и timezone для расчётов и графиков.

## 6. История звонков и карточка вызова

История в Web доступна Владельцу/Администраторам по всей организации, в Desktop сотруднику — только по своим вызовам. Таблица: дата/время, сотрудник, номер, транк, длительность, результат; фильтры период, сотрудник, транк, результат.

По открытию вызова:
- Заголовок: номер абонента, время, сотрудник, кнопка проигрывания записи при наличии.
- **Результат соединения** («Ответил человек» и иные технические статусы), AI-саммари **обычным текстом**, без бизнес-классификации. Понятно обозначать автоматическую генерацию.
- Краткие основные поля: длительность, транк, исходящий Caller ID.
- Две вкладки **«Транскрипт»** (спикеры, таймкоды, копирование) и **«Детали»**.
- «Детали»: полный, но структурированный технический блок **абонента**: phone, type, provider, **регион нумерации** (не геопозиция), country, timezone, код DEF/city_code; и блок **вызова**: trunk ID/название, Caller ID, SIP-код, причина завершения, начало/соединение/конец, длительность, привязка CRM, технические идентификаторы. Отсутствующие значения «Нет данных». Оператор по коду номера может отличаться от актуального после переноса.
- Не показывать сырые JSON и служебные HTTP-заголовки в UI, но сохранять техническую точность полей.
- Транскрипция и саммари **по умолчанию включены** для доступных записанных разговоров; обработка может завершаться позже факта звонка. Учитывать ошибки обработки/отсутствие записи.

## 7. Интеграции

Отдельный раздел сайдбара **«Интеграции»**: список подключений и кнопка **«+ Создать интеграцию»**. Типы: **amoCRM, Битрикс24, Webhook/API**. Несколько подключений/вебхуков — предполагаемый принцип, число и интерфейс управления уточняются по реализации. Подключение CRM необязательно для работы звонков. Документация публично доступна отдельно (планируемый адрес docs.sashatel.ru, ещё не опубликован).

**Общий сценарий CRM**
1. Администратор авторизует подключение и сопоставляет пользователя SashaTel с CRM-пользователем.
2. Сотрудник звонит **из Desktop**, а не из CRM.
3. Сразу после окончания разговор регистрируется в Desktop и Web; интеграция отправляет факт вызова и запись при наличии.
4. Асинхронно после AI-обработки добавляет транскрипт и саммари в связанную CRM-сущность.
5. Сопоставление по нормализованному телефону. Если однозначно найден контакт и одна релевантная активная сделка — допустима привязка к ней; при нескольких активных сделках — к контакту/сущности, **не выбирать случайную сделку**. При нескольких независимых контактах — не угадывать; сохранить результат в SashaTel и ошибку сопоставления. Номер неизвестен — сохранить в SashaTel. **Не** создавать автоматически лиды/контакты/сделки.
6. В amoCRM реализовать через нативные API звонков/примечаний; в Битрикс24 через API внешней телефонии и CRM binding; фактические права/методы проверить при реализации.

**Webhook**
- События **`call.completed`** и **`call.analysis.completed`** (AI готов позже), POST HTTPS с JSON.
- Группы полей: `event_id`, `event_type`, `timestamp`, `call_id`, `organization_id`, `trunk_id`, `employee_id`, `caller_id`, `phone_number`, `direction`, `status`, `hangup_reason`, `started_at`, `connected_at`, `ended_at`, `duration_seconds`, `billable_seconds`, `ring_duration_seconds`, `recording` (защищённый способ доступа), `analysis_status`, `transcript`, `summary` при доступности.
- Не копировать десятки полей SashaAI (`callList`, `skillbase`, `leadTransfer` и HTTP-заголовки) без соответствующей сущности SashaTel. Документировать типы, nullable, допустимые значения и версионирование схемы.
- Клиент задаёт HTTPS URL, выбирает события, получает секрет подписи, может послать тест. Подпись + timestamp, защита от replay, idempotency event_id, повторы с backoff и журнал доставок. Никаких публичных постоянных URL записи.

## 8. Тарифы, расчёты и биллинг

**Окончательное продуктовое решение:** фиксированная поминутная цена, **постоплата без кредитного лимита**. Клиент предполагаемо платит **3 ₽/мин SashaTel** и отдельно **3 ₽/мин Билайн**, суммарно ориентир **6 ₽/мин**. Это **две разные договорные и расчётные линии**. Тариф/состав услуг и округление Билайна должны быть реально согласованы с ним; SashaTel не устанавливает цену стороннего оператора. Не показывать в наших начислениях 6 ₽/мин как единый счёт SashaTel.

- У организаций индивидуальный согласованный расчётный период; у двух поставщиков периоды/даты должны синхронизироваться по договорённости. Фиксировать timezone и правило для последнего дня месяца.
- После завершения периода автоматически сформировать счёт на подлежащую оплате сумму и УПД **за фактически оказанные услуги**.
- Срок оплаты — **5 рабочих дней с даты выставления счёта**; просрочка блокирует **новые** вызовы, но не прерывает текущие. После подтверждённого получения денег новые звонки восстанавливаются автоматически. Просрочка и оплата **не сдвигают расчётный период/даты новых счетов**.
- Нет обязательного первоначального взноса/МГП и нет кредитного лимита. Допускается **добровольное пополнение**: клиент вводит сумму в Web, формирует счёт на пополнение; баланс изменяется только после фактического поступления средств. Платёж зачитывается в текущие начисления/задолженность, остаток — аванс следующих периодов. **УПД не возникает от самого факта формирования счёта на аванс**; авансовые налоговые документы определяются режимом НДС и бухгалтерской схемой, требуют юридической проверки.
- **Биллинг — одна страница:** сверху баланс, текущие начисления/срок платежа и форма «Сформировать счёт на пополнение»; снизу таблица **всех** счетов и УПД (автоматических и на пополнение), период, сумма, статус оплаты и **кликабельная иконка скачивания** PDF, не текстовая кнопка «Скачать»; документы хранятся исторически. В сайдбаре компактно отображать **«Баланс» и «Дата платежа»**; никаких «Следующий баланс».
- Долг не дублировать в следующих счетах; выставленные, оплаченные, частично оплаченные суммы и авансы учитывать отдельными проводками. Состояние оплаты подтверждать, а не менять только по нажатию кнопки создания счёта.
- **Открытые финансово-технические вопросы:** правила тарифной единицы (секунды/минуты, округление каждого вызова); согласование биллинга с CDR Билайна; налоговый статус, юридическая форма УПД/ЭДО, приём платежей, возвраты, спорные вызовы, механизм подтверждения оплаты, точные даты платежей. Без этих решений нельзя выпускать юридически значимые документы.
- Нет кредитного лимита => неограниченная экспозиция между платежами; признанный риск, но **не вводить скрытый лимит** вопреки решению.

## 9. Внутренний кабинет SashaTel

Видеть новые организации, транки/операторские заявки на удаление номеров, статусы провижининга/ошибки, интеграции и биллинг/документы/платёжные статусы; иметь аудит опасных изменений. **Не** добавлять настройки кредитного лимита как продуктовую функцию: от него отказались. Разделять операторские ручные действия и подтверждённые действия у провайдера.

## 10. Нефункциональные требования и приёмка

- Строгая tenant isolation: звонки, записи, документы, транки, секреты и события видны только в своей организации с соответствующей ролью.
- SIP и CRM-секреты шифровать и не возвращать plaintext. Повторные события и платежи идемпотентны. Источник истины о звонках — backend/CDR, не состояние браузера.
- Статусы «В сети/На линии/Не в сети» обновляются по реальным событиям/heartbeat, не по клиентским декларациям.
- Действительные возможности оператора по Caller ID, записи, тарификации и удалению номеров подтверждать интеграционными тестами.
- AI-статус «человек» не выводить из одного SIP 200; данные AI могут отсутствовать. Учитывать согласия на запись и обработку персональных данных, сроки хранения и удаление.
- Выгрузка и фильтрация должны быть консистентны с временными зонами и выбранным периодом.
- Приёмочные сценарии: организация/приглашение/роль; SIP подключение и fail-closed; вызов и автоматический Caller ID; статус «На линии» с момента набора; карточка звонка с деталями и транскриптом; корректный CSV; однозначная/неоднозначная CRM-привязка; защищённый webhook и повтор; расчёт 3 ₽/мин, аванс, УПД, 5 рабочих дней, просрочка/разблокировка, период не сдвигается.

## 11. Очередность реализации

1. **Критический сквозной путь:** Web организация и разрешения → подключение транка → работающий безопасный Backend/Telephony provisioning → реальный исходящий звонок Desktop → запись CDR и история.
2. **Телефония UX:** номера/авто-карусель, присутствие сотрудников, технические детали и диагностика, базовые агрегаты.
3. **Биллинг:** фактическая тарификация, проводки, счета, УПД, подтверждение оплаты, блокировки (юридическая/финансовая валидация до боевых операций).
4. **AI после звонка и интеграции:** запись/транскрипт/саммари; Webhook; amoCRM/Битрикс24. CRM click-to-call и персональные Caller ID — **не MVP**.

## 12. Нерешённые решения / не выдавать за готовую реализацию

- Последовательность Caller ID внутри активного пула (с соблюдением утверждённого равномерного распределения и лимита 8); ротация пассивных номеров **запрещена** решением v1.1.
- Точные тарифные правила и стоимость/возможности Билайна; платежный/налоговый процесс; юридические требования по записи/обработке.
- Наличие достоверного определения «Ответил человек», источников антиспам-меток, данных оператора/региона, текущего провайдера после MNP.
- Доступность и формат интеграций с CRM, разрешения на привязку записей; неоднозначные контакты.
- Проверка фактической готовности Live SIP и Asterisk, backend control plane, Desktop; наличие кода не равно end-to-end работоспособности.

**Примечание по веткам:** существующие Draft PR по Desktop, Backend и телефонии развиваются независимо; эта спецификация — продуктовый контракт, а не команда включить production вызовы до проверки инфраструктуры.
