# Интеграция веб-кабинета с API

Проверяемый коммит бэкенда указан в `web/backend-revision.txt`. GitHub Actions собирает фронтенд, применяет миграции к отдельной PostgreSQL и запускает браузер против этих версий фронтенда и API. `version.json` указывает проверяемую версию, а не состояние рабочего сервера. Почта и поиск реквизитов в интеграционном тесте используют тестовые адаптеры.

| Раздел | Состояние |
|---|---|
| Вход, регистрация, восстановление пароля, выход | API сессии, подтверждения почты и восстановления пароля |
| Организации клиента | Поиск реквизитов, создание, выбор и сохранение отображаемого названия через API. Юридическое наименование и ИНН меняются отдельным процессом |
| Внутренний кабинет | Список организаций, создание клиента, проверка, повторное рассмотрение, служебное чтение по UUID. Действия определяются полномочиями сервера |
| Внутренние сотрудники | Владелец видит реальный список, назначает роль по UUID существующего аккаунта с подтверждённой почтой, меняет роль и отзывает доступ. Поиск аккаунта по почте и приглашения требуют отдельного API |
| Ответственный менеджер | Назначение, сохранение и фильтрация требуют серверных данных о назначениях |
| Биллинг | Счета, баланс, начисления, списания и дата следующей оплаты требуют серверных контрактов |
| Транки | Текущий сервер Web не подключает TrunkService. Интерфейсу нужен контракт для Web-сессии, включая список, создание, настройки и номера |
| Звонки, статистика и записи | Нужны маршруты чтения с правами Web-сессии, проверкой организации и доступом к записям |
| Профиль и пользователи организации | Профиль читается из сессии. Для изменения данных, списка участников, ролей и приглашений нужны API |
| Интеграции | Нужны серверные маршруты и хранение реквизитов интеграций |

Страницы пользовательского соглашения и политики обработки данных содержат временный текст. Для оформления согласий нужны опубликованные документы и серверная фиксация версий.

## Новая страница или действие

1. В PR укажите маршрут, роли, область данных, формат ответа и ошибки. Для записи уточните, как API обрабатывает повтор запроса и конкурирующее изменение.
2. Используйте клиент `web/src/api.js` и тот же origin. Общий обработчик возвращает на вход после завершения сессии. Экран сохраняет введённые поля при сетевой ошибке. Если контракт ещё не доступен, покажите состояние недоступности до ввода данных.
3. Добавьте сценарий в `web/tests/browser.mjs` с реальным API и PostgreSQL. Подтвердите штатный сценарий, отказ для неподходящей роли или организации и сохранение после перезагрузки. Для действий с формами проверьте ошибку сети без подтверждения успеха.
4. При изменении серверного контракта обновите `web/backend-revision.txt` и перечень миграций в `.github/workflows/web-platform.yml`. Перед релизом сравните эту версию со сборкой целевого бэкенда и проверьте GitHub Actions на коммите фронтенда, который отправляется в Vercel.
