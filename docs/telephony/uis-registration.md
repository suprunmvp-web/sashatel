# Диагностика UIS REGISTER и допуск к PSTN

По последнему [отчёту Tech Lead](https://github.com/suprunmvp-web/sashatel/pull/15#issuecomment-6931578194), REGISTER выходит с VPS UDP 5062 к UIS UDP 5060. UIS сообщает об отправке 401. На входе VPS пакет к 5062 не наблюдался. Статус Rejected сам по себе не определяет причину. До получения 401 проверяется обратный сетевой путь. Первичный 401 обычно является Digest challenge.

## Один короткий интервал наблюдения

Выполняет владелец. Использовать очередную штатную попытку и согласовать с UIS точное окно UTC. Не включать pjsip logger, не сохранять PCAP и не выводить содержимое SIP. Команды ниже не меняют службу и firewall.

```bash
date -u +'%FT%TZ'
sudo ss -lunp 'sport = :5062'
ip -4 route get 195.211.122.91
sudo ufw status numbered
sudo nft list ruleset
sudo timeout 45 tcpdump -ni eth0 -nn -q -tttt 'udp and (src port 5062 or dst port 5062 or host 195.211.122.91)'
```

Фильтр принимает также ответ с альтернативного адреса/порта на 5062. Для защиты метаданных смотреть вывод локально. Перед передачей удалить посторонние адреса. Не передавать полный вывод nftables. Если UIS сообщает другой destination IP/port, повторить наблюдение с фильтром по согласованному адресу/порту. При необходимости посмотреть тот же интервал на any и сверить интерфейс. Timeout завершает захват автоматически.

Попросить UIS передать UTC timestamp, исходящий и входящий UDP 5-tuple, SIP status и обезличенный correlation ID. UIS должен подтвердить, какой source VPS он реально наблюдал, какой SBC отправил ответ и куда, отражён ли rport и совпадает ли destination ответа с наблюдаемым source REGISTER. Сверить Via received/rport без передачи SIP-заголовков целиком. Отдельно запросить полный список SBC и RTP адресов и портов через официальный канал.

| Наблюдение | Следующая проверка |
| --- | --- |
| REGISTER виден, ответ отсутствует на eth0 | Сверить 5-tuple с UIS. Проверить inbound cloud firewall, сетевые ACL Timeweb и трансляцию между наблюдаемым source и адресом VPS. Передать обеим сторонам окно UTC и tuples. Отсутствие пакета в захвате само по себе не локализует потерю у провайдера. |
| Ответ пришёл с другого SBC или порта | Сверить официальный профиль, stateful rule и фактический ingress drop. Любое изменение allowlist только после подтверждения UIS и согласования точного diff. |
| Ответ виден на eth0, статуса 401 у Asterisk нет | Сверить ingress counters, привязку сокета, адрес/порт назначения, routing и возможный NAT. Не отключать firewall для проверки. |
| 401 виден, повторный REGISTER отсутствует | На VPS проверить, что нужная registration ссылается на ожидаемый outbound_auth и transport. Сверить realm, URI, поддерживаемый Digest и локальные права файла. Передавать только статусы и счётчики. |
| После повторного REGISTER приходит 403 либо очередной 401 | Попросить UIS классифицировать отказ конкретной транзакции. Локально сверить auth ID, realm, algorithm, account block и зарегистрированный egress IP. Перевыдача секрета только по подтверждённой причине. |
| 200 OK после аутентификации | Подтвердить Registered в Asterisk и активную регистрацию в UIS. Проверить обновление регистрации на следующем интервале. |

CLI на VPS через существующий административный доступ: `pjsip show registrations` и `pjsip show transports`. Статусы записывать отдельно от client URI и auth ID. Если нужен прикладной SIP-разбор, поручить оператору отдать только коды и 5-tuples. Полный SIP trace может содержать Digest Authorization.

## Контракт provisioning для #19

Backend отправляет в доверенный provisioning worker версионированную команду с tenant/trunk ID и ссылкой на scoped secret в vault. Для UIS отдельно подтвердить registrar и proxy, UDP/TCP/TLS, auth realm и registration expiry, SBC/egress ACL, RTP/кодеки/DTMF, CLI, dial format и лимит одного канала. UIS-профиль держать отключённым по умолчанию. Worker рендерит отдельный приватный include атомарно, с правами root:sashatel-pbx 0640. SIP auth ID и пароль получает напрямую из vault. Команды, события и stderr не содержат секрета. Worker не принимает произвольный dialplan, путь или shell-команду.

Внешний transport и ACL изолировать от lab 10.50.0.1:5060. Изменения bind требуют отдельно запланированного restart с проверкой нуля каналов. Обновления registration применять под блокировкой на узел, с активацией одной версии за раз и сверкой loaded/registered/usable. Отказ проверки возвращает предыдущий include или выключает trunk с проверкой отсутствия его регистрации и сохранения lab. Хранить только идентификаторы версий и transition status. Публичный SIP/ARI по умолчанию закрыт. Фактическая конфигурация и live worker требуют отдельной реализации и тестов #19.

## Приёмка и откат

- Офлайн проверить версии, повтор одной команды, ошибочный tenant/secret reference, отказ регистрации и откат. На проверочной машине проверить доступность lab в обе стороны после применения и отката, отсутствие новых публичных listeners и редактирование логов.
- До PSTN подтвердить Registered, ограничение одного канала и недоступность trunk из Desktop SIP contexts. Реальный Backend/ARI пропускает только атомарно авторизованный dispatch. Изолированный операторский smoke, если отдельно согласован, допускает единственный фиксированный номер и один контролируемый вызов под явным разрешением владельца.
- Для разрешённого теста на обычный телефон подтвердить CLI и двусторонний звук, связанные CEL/CDR, тарификацию UIS и ноль каналов после завершения. Kill switch UIS проверять для новых попыток отдельно от активных каналов.
- При откате сначала запретить новых originate, завершить или дождаться текущего канала, отключить регистрацию, восстановить предыдущую версию конфигурации. Проверить оба SIP lab endpoint и сохранить обезличенные UTC/tuple/status. При диагностике только чтением достаточно дождаться завершения tcpdump.
