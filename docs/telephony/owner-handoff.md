# Допуск владельца к этапу B

Используем существующий WireGuard под wg-quick@wg0.service. Если сети нет, выделить отдельное окно для её настройки до допуска PBX. Владелец подтверждает ID VPS, консоль восстановления, fingerprint, snapshot, внешний IPv4/IPv6 и все текущие SSH пути. Для VPN нужны согласованные внешний IP и UDP порт, публичные ключи peers, три уникальных RFC1918 адреса, VPN /32 клиентов и отсутствие конфликтов маршрутов. На сервере AllowedIPs каждого клиента ограничен его /32, у клиентов серверный peer маршрутизирует только PBX /32. Оба клиента связываются с самим VPS, поэтому SSH, default route, NAT и forwarding для этой схемы не меняются. Приватные ключи остаются на узлах.

## Состояние по аудиту владельца

Ubuntu 24.04.5 x86_64, около 36 ГБ свободного диска и 3,4 ГиБ доступной памяти. На момент аудита UFW неактивен, WireGuard и Asterisk отсутствуют. SSH слушает IPv4 и IPv6, владелец вошёл root по паролю. Zabbix слушает TCP 10050 на публичном IPv4. Источник этих сведений — [комментарий Tech Lead](https://github.com/suprunmvp-web/sashatel/pull/15#issuecomment-6906848320). B.0 допускает только аудит и проверочные входы владельца. Настройка WireGuard требует отдельного согласования до установки PBX.

1. Оставить рабочий SSH-сеанс открытым. В консоли Timeweb проверить recovery login и сверить ED25519 fingerprint командой `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`. Независимо сверить его с доверенной записью на Mac. При несовпадении остановиться и проверить причину.
2. Со второго терминала Mac выполнить `ssh -vv -o BatchMode=yes -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -i ~/.ssh/<выбранный-ключ> <логин>@<VPS>`, заменив placeholders. Нужен новый успешный вход с подтверждением publickey в клиентском выводе. Self-SSH на VPS этой проверки не заменяет. При отказе сверить локальный публичный ключ с authorized_keys нужного логина, эффективный sshd config, владельца/режим home, .ssh и authorized_keys и журнал `journalctl -u ssh -b`. Исправления вне read-only аудита согласовать отдельно.
3. Подтвердить в панели завершённый snapshot/backup и доступ к процедуре восстановления. Для сетевого diff подтвердить у Timeweb, кто опрашивает Zabbix и с каких IPv4/IPv6 CIDR. Сохранить мониторинг, включить согласованный allowlist TCP 10050 в периметр и host policy, проверить доступ опроса после каждого шага. При отсутствии подтверждённых источников остановиться перед изменением правил для мониторинга.
4. Применять отдельно утверждённые изменения по одному слою. Сначала закрепить разрешённые пути SSH и мониторинга, затем настраивать WireGuard без изменения default route, после чего проверить оба peer. Перед сужением доступа проверить второй SSH-сеанс и мониторинг. Включение UFW выполняется отдельным шагом при открытой recovery console. После каждого слоя перепроверять SSH, мониторинг и WireGuard. При сбое восстановить последний изменённый слой через консоль.

## B.0 | Только чтение

```bash
ip -br address
ip -4 route show table all
ip -6 route show table all
sudo sshd -t
sudo sshd -T
sudo ss -lntup
sudo ufw status verbose
sudo ufw show added
sudo nft list ruleset
sysctl net.ipv4.ip_forward net.ipv6.conf.all.forwarding
systemctl is-active wg-quick@wg0
sudo wg show wg0 allowed-ips
ip -4 addr show dev wg0
ip -4 route get "${SIP_1001:?}" from "${PBX_IP:?}"
ip -4 route get "${SIP_1002:?}" from "$PBX_IP"
ping -I "$PBX_IP" -c 3 "$SIP_1001"
ping -I "$PBX_IP" -c 3 "$SIP_1002"
sudo wg show wg0 latest-handshakes
```

Отсутствующие утилиты и неактивная сеть фиксируются как недостающие предпосылки. Оба маршрута должны идти через wg0. С каждого клиента проверить route до PBX и ping с ожидаемого адреса VPN. Если ICMP уже блокируется, согласовать внутри VPN отдельную проверку двустороннего трафика в обоих направлениях и сверить peer counters. Handshake сам по себе недостаточен.

Убедиться, что есть второй проверенный SSH-сеанс по ключу и доступ в консоль. Владелец утверждает точный diff правил Timeweb, UFW IPv4/IPv6 и сохранение существующих routed policies, новый доступ из доверенных источников, порядок применения и способ восстановления. До активации поместить согласованные правила для всех путей управления, включая IPv6, и для WireGuard. При потере связи открыть консоль и вернуть сохранённые правила. При существующем UFW diff применяется после согласования, включая сами команды добавления или удаления правил. Если VPN, forwarding, IPv6 или текущие правила неизвестны, этап B остаётся на аудите.

Сохранить в приватном архиве с защитой от перезаписи Git SHA, версию образа, пакетный манифест, upstream checksum, хеш staged tree и журнал сборки. Архив хранить отдельно от конфигурации с секретами и логов звонков.

## Выдача и ротация

1. После установки владелец проверяет режим 0640 и группу sashatel-pbx на pjsip.conf и отсутствие staging config. В доверенной консоли без записи сеанса открыть файл в привилегированном редакторе с выключенными backup/swap либо использовать утверждённый vault importer, читающий файл напрямую. Не выводить секреты в shell, логи или историю команд.
2. Перенести значение password из auth-1001 и auth-1002 в две разные ограниченные записи менеджера секретов. Через vault выдать каждому оператору только его запись. Оператор вводит пароль в свой тестовый софтфон и очищает буфер обмена.
3. При ротации с нулём звонков отключить нужный клиент, заменить только его пароль новым случайным 256-битным значением из vault, сохранить владельца, группу и права, перезапустить PBX и обновить клиент. Проверить отказ со старым паролем и регистрацию с новым. Удалить старые записи и временные копии. Отозвать доступ к тестовому vault и VPN после теста.
