# SashaTel — инженерный handoff: Web Auth, Email, первый клиентский E2E

**Срез:** 21 ноября 2026. **Статус:** рабочий инженерный план и проверенный по GitHub inventory; не сертификат production-готовности.
**Ветка:** `feature/web-auth-production-20261121`. **Владелец изменений:** SashaTel Backend.
**Главная цель:** реальный пользователь проходит `platform.sashatel.ru` → регистрация с паролем → email-код → подтверждение → создание организации → кабинет, без ручных серверных действий.

## Архитектурное решение: транзакционная email-доставка

**Нынешняя проблема:** `WebAuth.deliverOne()` удерживает PostgreSQL `BEGIN` / row lock, пока вызывает `this.mail.send()` через сеть. Это создаёт зависимость блокировок БД от задержек и отказов почтового провайдера. `EmailSink` в старом сервере записывал коды в файлы и не мог обслуживать реальных пользователей.

**Требуемое устройство (сначала Auth, без отдельной message-broker инфраструктуры):**

1. При регистрации в одной транзакции создаются challenge + encrypted outbox job. API возвращает принятый запрос, **не** гарантированную доставку.
2. Worker краткой SQL-транзакцией атомарно забирает due job, выставляет случайный `lease_token` и `lease_until`, фиксирует транзакцию. Захват конкурирующими worker исключается `FOR UPDATE SKIP LOCKED`.
3. После commit выполняется запрос к provider **вне транзакции** с детерминированным idempotency key, привязанным к challenge.
4. Успех/ошибка записываются только через fencing условие `WHERE challenge_id=? AND lease_token=?`; старый worker не вправе менять состояние нового владельца lease.
5. Временные сетевые ошибки, 429, 5xx — backoff с jitter и ограничением попыток/срока challenge; постоянные ошибки 4xx (кроме 429/отдельных временных) — terminal, без бесконечных запросов. Не логировать email/code/API key/envelope.
6. После crash lease истекает и другой worker может повторить запрос с тем же idempotency key. **Exactly-once физическая доставка невозможна** при неизвестном результате сети; зависим от семантики/срока хранения idempotency у провайдера.
7. Challenge может истечь или быть заменён при resend: worker до отправки проверяет expiry, consumption, актуальность привязки браузера/челленджа. Операции подтверждения/повторной регистрации не должны создавать рабочие старые коды.
8. Не отмечать "delivered" после успешного HTTP API ответа: это только `accepted` провайдером; для `delivered/bounced` потребуются подтверждённые подписанные webhook-и (отдельная задача).
9. При shutdown worker прекращает брать новые задачи и корректно завершает текущую; lease остаётся механизмом восстановления после аварии.
10. Тестовая `MailPort`-заглушка остаётся в `*.test.ts`; файл-записывающий `EmailSink` не должен попадать в runtime path. Никакой отдельный Redis/RabbitMQ не добавляем без подтверждённой необходимости.

**Недоделка в текущем `resend-mail.ts`:** пока все HTTP ошибки бросаются одинаково; перед релизом необходимо классифицировать permanent/transient, покрыть timeout/повторы и проверить фактический контракт idempotency Resend (включая сроки хранения). Код и subject письма — чувствительные данные: не хранить/выводить в телеметрии.

**Миграции:** не редактировать применённую `004-web.sql`; новая `007-mail-lease.sql` additive. В `migrate.ts` миграции проверяются по checksum; обязателен контроль runtime прав, откат на уровне приложения и совместимости схемы.

## Auth / Web / tenant security: обязательные инварианты

- **Регистрация с паролем остаётся утверждённой**, не заменять входом по email-коду без пароля. Шестизначный код подтверждения помещается в **тему письма**, тело содержит тот же код; `autocomplete="one-time-code"` в Web. Gmail quick-copy — ожидаемая возможность клиента, не гарантированная функция нашей платформы.
- Защитить от account enumeration; TTL и попытки кода, rate limits на регистрацию/resend/login, повторные запросы, отказанные/истёкшие challenge, безопасный lost-response recovery.
- Session cookies HttpOnly/Secure/SameSite и точные Origin/CSRF проверки на сервере; refresh rotation/reuse protection; logout и смена организации не должны оставлять действующих старых контекстов.
- `platform.sashatel.ru` должен обращаться к backend через проверенный same-origin proxy `/v1/*` с корректными `Set-Cookie`/Host/Origin и без обхода CSRF. Считать эту интеграцию **непроверенной**, пока не пройдёт browser E2E.
- Создание организации: атомарные owner + membership + subscription; повтор по idempotency key не создаёт дубликат; RLS/tenant isolation проверяются реальной PostgreSQL.
- Интеграция DaData для ИНН: сейчас опционально задан `DADATA_API_KEY_FILE`; при отсутствии ключа lookup завершается ошибкой, путь организации end-to-end блокируется. Нужны конфигурация и договорные условия.
- Серверные secret files, минимум прав, структурированные логи без персональных данных и секретов, readiness vs feature health отдельно.
- Не раскрывать логически различные ошибки, позволяющие узнать о существовании адреса; провести abuse-тесты и проверить допустимость повторного информационного письма для существующих аккаунтов.

## Правила передачи следующему разработчику / чату

1. **Прежде чем менять код**, читать канонический продуктовый handoff + ТЗ, затем этот инженерный handoff, проверять GitHub ветку/PR и актуальное окружение. Не пересогласовывать утверждённое.
2. Разделять **запланировано → закоммичено → тесты пройдены → staging развёрнут → E2E подтверждено → production**.
3. Не делать вывод о готовности по `/ready`, коммиту, открытому PR или SIP `Registered`.
4. Фиксировать каждый существенный архитектурный выбор как проблему, альтернативы, причину, инварианты, тесты и миграционный риск.
5. Пока нет законченного P0+P1, **не менять текущий работающий контейнер и не применять 007 на сервере вручную**.
6. Secret/token/password не копировать в репозиторий, коммиты, логи или сообщения. Защита от случайного разглашения важнее удобства отладки.
7. Не превращать подготовительные предложения (выбор Resend, внешний лендинг на `sashatel.ru`) в утверждённые продуктовые решения. **Лендинг поставлен на паузу**, фокус — клиентская платформа.
